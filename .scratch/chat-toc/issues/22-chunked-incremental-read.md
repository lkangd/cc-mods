# 22: Chunked and incremental reads of large files

**What to build:** A transcript over 4 MiB still gives the full contents; as the session goes on, only the new part is read and only the last group is regrouped; when the file cannot be read or holds unrecognized lines, the Pane says so truthfully and does not piece together a list posing as the complete contents.

Spec: [chat-toc MVP](../spec.md) §3.

**Blocked by:** 17 (The minimal docked contents)

**Status:** resolved

- [x] On the first read when the file is over 4 MiB, and on any incremental read, on macOS/Linux read 4,000,000 B from a byte offset with `dd` to seek plus `head`; on Windows build a Windows PowerShell 5.1 `[IO.File]` command that reads by offset and prints base64
- [x] Each chunk is cut at its last newline, and the offset advances by the UTF-8 byte count of the part kept; when a half row crosses a chunk edge the result equals a whole read (CT-DATA-004)
- [x] A single line longer than one chunk is counted as an "unrecognized line" and skipped
- [x] When the file shrinks, it is re-read whole; when the new leaf can walk back to the old chain's last row, the old chain is kept and only the last group is regrouped from its opening row, otherwise the whole is regrouped; the incremental result equals the whole regroup group by group
- [x] On a read failure or no permission, no entry shows and the bottom keeps the reason, with no list pieced together from `$.session.messages()` (CT-DATA-002)
- [x] Unrecognized lines are skipped, and the bottom says "N lines not recognized; the contents may be incomplete", N the real count (CT-DATA-003)
- [x] Automated tests cover chunk edges, half rows, over-long lines, and incremental equal to whole; Linux and Windows use only a `$.process.run` stand-in to check the command built and the output parsed

## Comments

**2026-10-10 implementation notes (branch `chat-toc/22-chunked-read`)**

- Modules: `source.ts` is the pure chunked reader (`readChunks` loops over chunks, cuts each to its last newline, and advances the offset by the UTF-8 byte count of the part kept; `chunkCommand`/`chunkText` build the `sh -c 'dd … ; head -c …'` or Windows PowerShell 5.1 command and parse its output); `regroup.ts` is the incremental model (`readLines` merges new whole lines into the index; when the new leaf's walk back meets the old chain's last row, the old chain is kept and only the last group is regrouped from its opening row with `groupTurns`, otherwise the whole is regrouped); `chain.ts` is split into a growable `ChainIndex` plus `walkBack`, with `currentChain` behaving as before. `model.ts`'s `tocModel` is no longer used by register and stays as the "whole regroup" criterion in tests. `register.tsx` gains only `runChunk` (the one place that calls `$.process.run`) and the read state.
- Incremental equal to whole: the tests take only `tocModel(whole text)` as the criterion and write no grouping rules, so they stay valid after ticket 19 changed the rules. The premise is that grouping looks only at the rows themselves and a group's contents depend only on the rows between its opening row and the next opening row; if 19 brought in context across groups, these random tests would fail. When the same uuid is written again, the whole is regrouped.
- Starting point: the first read (or a restart after the file shrank or a read failed) with a file of 4 MiB or less uses `$.fs.read`, and if `fs.read` fails it goes to chunks (the case of a file that grew past 4 MiB after the stat); every other read is chunked from an offset. A half-written last line is left for the next read.
- Over-long lines: when a whole chunk has no newline and the file holds a full chunk at that place, it enters the "skip" state and advances by bytes until the line ends, only then counting 1 unrecognized line; while this line is still being written, the skip state is kept across several reads and is not counted twice. When advancing by chunks, a multi-byte character cut at the chunk's end (the host decodes it to U+FFFD or drops it) is not counted into the offset, and the next chunk rereads from its first byte.
- **Windows chunk size deviates**: Windows reads 3,000,000 B per chunk, not 4,000,000 B. Base64 grows the output by 4/3, and `$.process.run` keeps only the first 4 MiB (4,194,304 B) of stdout; the base64 of 4,000,000 B is 5,333,336 B and would be cut, while the base64 of 3,000,000 B is exactly 4,000,000 B. The path, offset and byte count pass through the environment variables `CHAT_TOC_PATH/OFFSET/BYTES` rather than the script, which avoids PowerShell quote escaping; the file is opened with `FileShare.ReadWrite`. Whether it is Windows is judged by the transcript path (a drive letter or UNC). Only stand-in tests; not run on a real Windows.
- Failure (CT-DATA-002): when stat/read/command fails the entries are cleared, and the Pane's last line keeps "No permission to read this session's transcript; nothing to show" (EACCES/EPERM/permission/UnauthorizedAccess) or "Cannot read this session's transcript; nothing to show"; the next read starts over from the beginning. With no entries this line is the body's only line (drawn at the very top, with no blank line padded above). `$.session.messages()` is not called.
- Unrecognized (CT-DATA-003): after the entries a line stays: "N lines not recognized; the contents may be incomplete", N accumulating lines that failed to parse and over-long lines, not counted twice by incremental reads. The former "transcript is over 4 MiB, the contents cannot be read for now" is deleted.
- Tests: `claude plugin test mods/chat-toc` 52 all pass (2.1.295); new are `chunked_read` (each chunk size, half rows, half characters, over-long lines including the still-being-written case), `incremental_regroup` (append, a rewind's new branch, sidechains and bad lines, a rewritten same uuid, 40 random sessions with random slices compared to the whole) and `transcript_source` (the `dd`/`head` command and offsets for over 4 MiB, appends reading only from the offset, a half-written last line, a shrunk file re-read, no permission, recovery after a read failure, the bad-line count at the bottom, over-long lines, the Windows PowerShell command and base64 parsing). `tsc` has 0 errors against the 2.1.287 and 2.1.295 declarations; `claude plugin validate` passes on both versions (`$.process.run (via runChunk)`).
- PTY (cmux, its own workspace, other plugins off, a synthetic 9.9 MB transcript: 60 groups, 2 bad lines, 1 non-chain line of 4.1 MB, `--resume`, deleted afterwards):
  - 2.1.295: after `/chat-toc` opens it, C000 to C059 are all listed (scrolled to the top and bottom to confirm), and the last line reads "3 lines not recognized; the contents may be incomplete"; after that, the rows a real round of conversation appended, read incrementally, left the entries and the count unchanged (no double counting).
  - 2.1.287: the same session resumed, with the same chunked result; after `chmod 000` on the file and a hot reload, the Pane held only "No permission to read this session's transcript; nothing to show"; with the permission restored and another hot reload, the entries came back.
  - The terminal was only 113 columns and did not dock by itself, so it was opened with `/chat-toc` (docking is possible at 110 columns or more at request time).
  - "A new group appearing after an incremental read" was not seen in the real host: that needs a human prompt submitted, and this synthetic session's context is 973k tokens, so one `!echo` made the host start a model round (about $0.96, the 5-hour quota used up to 97%), and nothing more was submitted. The `transcript_source` append test covers this point.
