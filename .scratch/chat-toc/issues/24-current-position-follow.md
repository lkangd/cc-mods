# 24: The Current position highlight and the TOC following

**What to build:** The contents highlight in cyan the turn the person is looking at and scroll to it by themselves; after a jump the highlight locks on the target group until the viewport changes again; a manual scroll of the contents pauses following and shows "paused", which resumes at the transcript viewport's next change; while the Pane is in a background tab it does not draw, and on the first frame back in the foreground it catches up.

Spec: [chat-toc MVP](../spec.md) §6, §2 (coexistence).

**Blocked by:** 23 (Full jumps: the Agent side, fallbacks and refusals)

**Status:** resolved

- [x] Look only at the on-screen reports of `UserMessage`, `AssistantMessage`, `CommandOutput` and `ToolGroup`; a record reported `null` is deleted at once; the ordered array of drawable rows is rebuilt only after a read finishes and when a new row is drawn
- [x] On-screen rows are cut into runs in conversation order; only the run holding the latest report is believed and its first row taken, assigned to the group it belongs to (to the previous group when it belongs to none); whether a not-on-screen drawable row sits between is judged by binary search
- [x] When the last drawn row is wholly visible, the last group is forced; after a successful jump the target group is locked, and the first change of the viewport after the redraws caused by the jump stop unlocks it (CT-POS-001)
- [x] After 180 notches of continuous wheeling, the highlight matches the group of the screen's first row (CT-POS-002)
- [x] The transcript render hook writes the `$.state` atom with `$.clock.after(0, …)` only when the value really changes, and the Pane reads it to redraw; no direct write in the render hook, no `Promise.then`, no unconditional invalidate
- [x] The TOC follows the highlight; a manual scroll of the TOC or the Pane being focused pauses it, and the footer shows "paused"; it resumes at the Current position's next change (CT-POS-003); the scrolling is managed by the plugin itself, with no `$.ui.scroll({ to: "end" })`
- [x] While not in the foreground (`isShown === false`), a change of the Current position cancels the pause, and the first frame back in the foreground follows (CT-COEX-001)
- [x] After a hot reload the map is rebuilt once the transcript is read, and jumps and the highlight stay right (CT-LIFE-006)
- [x] The highlight and the ↑↓ selection cursor are drawn separately
- [x] If "View filter, three Layouts and the keyboard" is done, add "with no selection cursor, a Layout switch anchors on the group of the Current position"
- [x] Automated tests cover the contiguous-run algorithm; the PTY acceptance of the scenarios above passes on both versions

## Comments

2026-10-11, branch `chat-toc/24-position` (based on `chat-toc/mvp` ce384e1, with 3f38f30 merged in).

- **Code**: `hooks/position.ts` (pure functions): the ordered array of drawable rows `drawableRows` (rebuilt after a read) and `addDrawable` (a newly drawn row is inserted by binary search), `trustedRun` (cuts into runs in conversation order, cutting where a not-on-screen drawable row sits between two rows, judged by binary search; takes the run holding the largest `seq`), `positionOf` (lock > last row wholly visible forces the last group > the group of the run's first row; the group is found by binary search on the opening rows' positions, `groupOfRow`, and rows before the first group do not light), and the jump lock `lockOn`/`viewChanged`/`quietAfter` (the 300 ms quiet time is timed by `$.clock.after`, so tests can control it). `window.ts` gains `topFollowing`. In `register.tsx`: in the site render hook, `sawSite` records the report and then `place()` recomputes, and only when the value changed does `$.clock.after(0)` write the new `$.state` key `currentGroup` (-1 meaning nothing lights); the Pane reads it to draw `litGroup` and to decide on following; after `load()` finishes it rebuilds the opening-row table and the drawable rows, and recomputes from the last drawn row (so a draw-before-read at a hot reload is recovered too); a successful jump calls `lockAfterJump`.
- **Following and pausing**: when not paused, the window follows the highlighted group (the last group or, with no highlight, the newest; if the highlighted group's first entry is already in the window it does not move, otherwise it makes it the window's 2nd entry). A manual scroll of the Pane pauses; while the Pane is focused it stays paused (focus sets the pause, and after blur it waits for the Current position's next change to resume; a change during focus counts as the "next change" on the first frame after blur). The footer's "paused" ranks after the refusal notice and the data source's note. When the Pane is in a background tab (`isShown === false` in `$.ui.panes()`), a highlight change cancels the pause at once, and `panes()` is queried only when already paused.
- **The anchor for a Layout/filter switch**: with a selection cursor, the cursor's group (the original logic); with no cursor and following, no anchor (following itself keeps the highlighted group in the window); with no cursor and paused, the Current position's group, moving the window only if it is outside it, the paused state unchanged; with no highlight, the group at the top of the window (the original logic).
- **Trade-offs / host facts**:
  - Drawable rows count only "the rows the host certainly draws at a site": the prompt (`UserMessage`) and the assistant rows with text (`AssistantMessage`), plus any row a site has drawn. **In a session opened by `--resume`, a local command's output row (`system/local_command` stdout) does not go through the `CommandOutput` site** (measured with a probe: resuming 300 turns and scrolling past `/tui`, the `CommandOutput` hook was never called once; a `/diff` newly run in this session does go through it); if it were counted as drawable in advance it would never be on screen, cutting the on-screen rows before and after it into two runs, and scrolling down the highlight would jump to the next group (CT-POS-002 failed exactly this way in the PTY's first round). Tool rows likewise count only once drawn.
  - The known limit that follows: for the `!cmd` group (which never has a site at any time) and for a local command's group in a resumed session, when only those rows show at the very top of the screen the highlight lands on the next group. The spec's algorithm looks only at the four sites, so it cannot see these rows to begin with; the PTY criterion therefore takes the group as "the first prompt/reply row counting down from line 1" (`sitedTop`), and also records the literal first line (`top`); the two differed once on each version (both on top of the `/tui` group). This is written into the root README draft's "cyan highlight" item.
  - "Viewport change" = some site's `onScreen` differs from the one recorded (newly appearing, value changed, reported `null`); a same-value re-report does not count as a change (no unlock, no side effect beyond the recompute) but does refresh `seq`, because the host is really drawing it.
  - `onScreen` records are not cleaned over time: after long scrolling the leftover records grow, and the recompute on each report is O(n log n); left for ticket 27 to look at when testing long sessions.
