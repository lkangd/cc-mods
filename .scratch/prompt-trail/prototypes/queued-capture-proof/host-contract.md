# Issue 35 · 宿主关联契约需求草案

## 状态与范围

2026-10-01。本文把现有 composer 捕获协议和已对齐的 Q1–Q3 转成宿主能力要求，**不是已存在的 API、已批准的协议修改或可直接实施的修复**。仅保存在本地研究目录，未向宿主维护者发送。

本文不要求改写正常提交的正文、context 或 origin，不使用注入标记、文本摘要、时间或渲染身份补桥。正式 hooks/helper/schema/制品不变。真实实验及任何正式实现仍需另行批准。

## 保持不变的边界

- 资格仅来自启用且健康 Run 的 composer-origin `prompt.submit`；host receipt 只证明该资格的结果，不反向创建资格。
- 先持久预写 Pending Capture，再调用 next。预写失败仍可 drop 并保留草稿；queued return 不确认 Entry，也不推进 Active Branch。
- 保留最终 submit.text，只保留附件数量与宽泛类型。不能用整行 API content 替代提交全文，不能保留附件内容、名称、路径或哈希。
- 唯一进入证据才确认，唯一撤回证据才丢弃；健康 waiting 允许继续排队。歧义或持久写失败保留 pending 并阻断后续采集，显式对账取消不结算。
- transcript、classic、render 与新 append 都不能独立补成员；load/resume、reload 和 fork 不能靠旧同文消息自动确认。

依据：项目 spec 第 7–8 节、Issue 13/15 和 Issue 35 的 Q1–Q3。旧 Issue 13/15 中“next 返回就确认”及“完整 transcript 中没有同文就丢弃”的历史判据，不作为活跃队列场景的正确保证。

## 最小实时能力

以下描述语义，不规定宿主字段名或方法名；符号身份仅供手算样例，不是实际记录。

| 能力 | 必须保证 | 不能替代它的证据 |
| --- | --- | --- |
| 提交关联身份 | 每次 composer submit 在产生进入/排队副作用前获得固定、非正文身份；不同提交即使同文也不同。身份作用域含明确的 conversation/宿主世代，跨恢复不能误用其他提交的身份 | 当前运行 turnId、classic prompt_id、render requestId、时间、正文、调用对象引用 |
| 全链路对应 | 身份随该提交经过下游改写、排队、出队、进入和撤回；不能由其他来源伪造，也不能因改写丢失。插件可把它与自己预写的 eventId 绑定，不把 eventId 注入模型上下文 | submit.after 与 append 时间相近，或各事件都带 composer 来源 |
| 实际进入 receipt | 仅在该提交对应的实际 conversation 内容被保留后给出进入结果及稳定行引用；队列预览和 enqueue 不算进入。说明一条逻辑提交与物理行的基数和承载位置 | append 出现一条同文行、dequeue、turn.start、turn.complete |
| 实际撤回 receipt | 精确标识被撤回且尚未进入的提交。批量 popAll 必须给出完整成员集合及其作用域；不包含已出队或随后新增项。异常/取消不能一律等同撤回 | 未见 user 行、next.signal 中断、模块 reload、空队列快照 |
| 因果与终局 | 身份的排队/处理中与终局可区分；entered/withdrawn 不互相覆盖。重复通知不改变事实；事件先于 submit.after 到达也可关联。事件丢失或未知必须可感知 | 回调完成顺序、日志落盘顺序、仅有 append 链内顺序 |
| 最终文本边界 | 本次 submit 的最终 text 与资格身份可关联；下游 context、内部附件、后续行改写不被拼入全文。drop/异常/未取得最终文本时不得自动确认 | 将 append.content 的所有 text blocks 拼接，或使用预写的未改写文本冒充 final text |

这组能力同时覆盖“正常出队”和“精确撤回”。仅增加 append 上的共享身份能改善进入关联，但没有撤回 receipt 时仍不能自动丢弃；不能因此宣称整个 Issue 35 已可实现。

## 恢复与持久边界

最小安全方案可以在宿主不能恢复 receipt 时退到 Q3 显式对账；不要求把所有重启都变成自动恢复。但若宣称支持自动恢复，至少还需以下契约：

1. 提交身份、已取得的 final-ready 状态与最终全文要在确认前完成持久关联。正文只进现有 SQLite 档案与宿主 transcript；store/诊断仅保留非正文身份。具体 helper/schema 设计本轮未定。
2. 宿主按同一身份提供可验证的终局重放或状态查询；说明读取范围、保留期限、截断、失效、旧进程与当前 conversation 的绑定。不返回终局不等于 withdrawn。
3. 丢失事件、损坏/截断、会话改绑、fork、compaction、部分读取及未知来源产生明确缺口。旧 receipt 不能用于新的 Run、Conversation Segment 或 Archive generation。
4. receipt 的行引用用于实际进入证明；Active Branch 的父节点仍需依据正确活动路径结算。多条 pending 不提前成为彼此可确认的父节点；不能靠 receipt 到达顺序决定父链。
5. 档案确认与分支更新失败仍保留可发现、可重放的恢复状态。重复处理同一 receipt 只产生一个 Entry；已确认后不能用后续 popAll 撤掉它。

receipt 不是新的正文存储通道；没有必要让取消事件携带文本或附件信息。

## 手算验收样例（尚未写测试、尚未实测）

这里的 A/B/C 是三个不同 composer 资格，X 是非 composer 输入，uA/uB 是存储行引用。样例只规定可观察行为，不规定实现结构。

| 场景 | 独立期望 |
| --- | --- |
| A/B 正文完全相同，A 进入 uA、B 撤回 | 恰好确认 A，丢弃 B；下一条 C 的父节点为 A，不因缺少 B 误判 rewind |
| A 已出队但未取得进入 receipt，popAll 撤回 B | A 仍未确认且不可被该 popAll 丢弃；B 可唯一丢弃。A 后续进入才确认 |
| popAll(B) 之后新增 C | 撤回只影响 B，不影响 C；需要成员身份，不能把采样时所有 pending 当作同批 |
| X 的进入/撤回夹在 A/B 中间 | 不为 X 创建资格或 Entry，不把 X 的行或队列操作绑定给 A/B |
| A 的进入 receipt 早于 submit.after | 关联仍唯一；在最终文本未取得并持久 ready 前不确认，之后只确认一次 |
| A 被下游改写 text，并额外注入 context | Entry 保存最终 submit.text，不保存 context、附件内容或 append 后续改写；身份不因改写变化 |
| A 预写失败 | 不调用下游进入路径，不出现 A 的 Entry，保留或如实报告无法恢复的草稿 |
| A 已进入，确认写失败或分支更新失败 | 保留恢复状态，阻断新采集；重复 receipt/恢复不产生第二个 Entry |
| reload 后 receipt 缺失或查询截断 | 保留 pending，显式对账；取消继续保持未决，不按旧同文或无行推断 |
| 宿主给同一身份冲突终局，或未说明多物理行映射 | 视为无法证明，不任意挑一个结果，不自行改变成员资格或全文规则 |
